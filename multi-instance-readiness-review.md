# IbkrConduit — Multi-Instance Readiness Review

_Generated by a multi-agent review across 6 lenses; every finding was re-verified against source by the adjudicator._

## Overall verdict: Ready with caveats

The library genuinely upholds its CLAUDE.md goal of "no global or static mutable state." A direct sweep of `src/` confirmed **zero mutable static fields**; all per-credential runtime state lives on per-provider instances. Under the supported hosting model — **one `IServiceProvider` (one `AddIbkrClient` call) per credential** — N instances are fully independent: independent brokerage sessions, independent WebSockets and subscription registries, independent order/question-reply flows, and independent global + per-endpoint rate-limit budgets. No cross-account data leakage or wrong-account signing path exists in that topology. Two caveats keep this from an unqualified "Ready": a registration foot-gun if a consumer hosts two credentials in one shared container (silent pipeline corruption, no guard), and a uniform observability gap (no tenant dimension on any telemetry), which makes per-account monitoring impossible in exactly the multi-instance process this review targets.

## Scenario

A single .NET process hosts MULTIPLE concurrent IbkrConduit instances, each configured with a DIFFERENT set of IBKR OAuth 1.0a credentials. All run simultaneously and must be fully independent — own session lifecycle, own WebSocket(s), own order/question-reply flow, own rate-limit budget. The expected pattern is one DI registration (one `IServiceProvider` / one `AddIbkrClient`) per credential. The review question: does the library hold any process-global or shared mutable state that would make instances interfere, leak data across accounts, throttle each other, mis-route orders, or assume only one instance is active?

## Findings

### Medium

### No per-tenant/account dimension on any metric, span, or log — accounts are indistinguishable in a multi-instance process — `Medium`

**Location:** `src/IbkrConduit/Diagnostics/LogFields.cs:11-12`; `src/IbkrConduit/Auth/OAuthSigningHandler.cs:96-103`; `src/IbkrConduit/Session/SessionManager.cs:161,273,305`; `src/IbkrConduit/Session/TickleTimer.cs:169-211`; `src/IbkrConduit/Streaming/IbkrWebSocketClient.cs:372,491,518,607`; `src/IbkrConduit/Http/GlobalRateLimitingHandler.cs:58,81`; `src/IbkrConduit/Http/EndpointRateLimitingHandler.cs:66-67,90-92`; `src/IbkrConduit/Client/MarketDataOperations.cs:78,98,122-141`.

**What the code does:** The `ActivitySource` and `Meter` are correctly single process-global instances named `IbkrConduit`, and every metric instrument is `static readonly` built from that `Meter` (correct OTEL pattern). A `LogFields.TenantId` constant (`"ibkr.tenant_id"`) is defined for exactly this purpose, but I verified by grep that it is **never** attached to any `Activity` tag, metric `TagList`, or log scope anywhere in `src/` — its only runtime use is naming the LST/Flex `HttpClient`s. HTTP request metrics tag only endpoint/method/status; session counters (`_activeSessionCount.Add(±1)`, `_refreshCount`), tickle counters, WebSocket message/reconnect/heartbeat counters, and rate-limiter wait/reject metrics carry no tenant tag. Operation spans tag `AccountId` only when an account id is a method argument — that is the IBKR sub-account being acted on, not the emitting credential/instance identity.

**Impact on multi-instance:** All instances feed the same `Meter`/`ActivitySource`/log categories with no dimension identifying which credential emitted a value. A consumer running several credentials in one process cannot attribute throughput, errors, session churn, reconnect storms, or rate-limit saturation to a specific account. This is an attribution/operability gap, **not** functional interference or data leakage — isolation is intact; only observability is lost.

**Recommendation:** Stamp the credential's `TenantId` (already available on the injected `IbkrOAuthCredentials`) as a dimension at emit time — add it to the `TagList` on metric `Add`/`Record` calls, as a span `SetTag` (the `LogFields.TenantId` constant already exists), and/or establish a per-instance `ILogger.BeginScope`/`Activity` scope at the pipeline boundary. The instruments can stay process-global; only the emitted measurements need the tag.

**Confidence:** High. Raised by all six lenses; verified `LogFields.TenantId` has no telemetry call sites.

### `AddIbkrClient` called twice on one `IServiceCollection` silently corrupts the pipeline (last-wins singletons + accumulated Refit handler chains), risking wrong-account signing — `Medium`

**Location:** `src/IbkrConduit/Http/ServiceCollectionExtensions.cs:36-86`; `src/IbkrConduit/Http/ConsumerPipelineRegistration.cs:82-118`; `src/IbkrConduit/Http/RateLimitingAndResilienceRegistration.cs:21-22`; `src/IbkrConduit/Http/SessionServiceRegistration.cs:68`.

**What the code does:** Every service is registered via plain `AddSingleton` — no keyed DI, no `TryAdd`, no marker/guard (verified: grep for `AddKeyed*`/`TryAdd*` returns only the two `AddRefitClient` lines, nothing keyed). The 9 consumer Refit clients and the internal session client use `services.AddRefitClient<TApi>()`, whose `IHttpClientFactory` logical name defaults to the interface type name (no tenant qualifier). `OAuthSigningHandler` captures `credentials.ConsumerKey`/`credentials.AccessToken` in the registration closure (`ConsumerPipelineRegistration.cs:114-118`). Therefore a second `AddIbkrClient` on the same collection: (a) re-maps each Refit interface to the **same** client name and **appends** a full duplicate handler chain — including a second `OAuthSigningHandler` closed over account B's keys — onto account A's client; and (b) makes the `ISessionManager`/`ISessionTokenProvider`/`IIbkrClient`/`RateLimiter`/options singletons resolve last-wins, so both accounts share one session manager and one limiter budget. Note the LST and Flex *plain* clients ARE tenant-named (`IbkrConduit-LST-{TenantId}`, `IbkrConduit-Flex-{TenantId}`), so they survive — which masks the failure: LST acquisition looks fine while the facade/session/Refit signing are cross-wired.

**Impact on multi-instance:** Under the documented one-provider-per-credential model this never triggers and isolation is total. But a consumer who intuitively registers two credentials in one container gets a silently broken pipeline — exactly the cross-account credential-bleed / wrong-account order-routing class of bug — reached with no error or warning at registration time. The asymmetry (LST/Flex tenant-named, consumer Refit clients not) makes the misuse non-obvious.

**Recommendation:** Add a registration guard (detect a marker service already present and throw a clear "AddIbkrClient already called; host one IServiceProvider per credential or use the keyed/factory API" exception), and/or provide a first-class keyed multi-instance API (`AddKeyedSingleton` keyed by `TenantId`, or an `IIbkrClientFactory`). Tenant-name the consumer Refit clients to match the LST/Flex clients. At minimum, document in `AddIbkrClient`'s XML doc that it must be called at most once per `IServiceCollection`.

**Confidence:** High (mechanism verified). Severity held at Medium because it occurs only under the unsupported single-container topology; the supported model is unaffected.

### Low

### Per-instance `ObservableGauge`s registered on the process-global `Meter` with no tenant dimension and never disposed — `Low`

**Location:** `src/IbkrConduit/Streaming/IbkrWebSocketClient.cs:97-99` (`ibkr.conduit.websocket.connection_state`; `DisposeAsync` at 241-274 does not unregister it); `src/IbkrConduit/Http/GlobalRateLimitingHandler.cs:45-48` (`ibkr.conduit.ratelimiter.global.queue_depth`).

**What the code does:** Both gauges are created in instance constructors via `IbkrConduitDiagnostics.Meter.CreateObservableGauge(...)`, each closing over that instance's `_webSocket`/`_limiter`. They carry no tenant tag, the returned instrument is not captured, and it is never disposed. A new WebSocket gauge is registered per client instance; a new queue-depth gauge is registered per `GlobalRateLimitingHandler`, which `IHttpClientFactory` rotates (~2 min default), so callbacks accumulate.

**Impact on multi-instance:** N instances register N callbacks under one identical instrument name+tags, producing OTEL duplicate-instrument warnings and ambiguous merged readings (cannot tell which account's socket is up or whose queue is deep). Retained callbacks also pin references to rotated/disposed handlers — a slow leak. Telemetry-clarity/robustness only; no throttling or socket-isolation defect.

**Recommendation:** Add the tenant id as a measurement tag, capture the returned instrument and dispose it in `DisposeAsync`, and prefer registering queue-depth once (e.g. via the per-provider `HealthStatusCollector`, which already holds the limiter) rather than in every handler constructor.

**Confidence:** High.

### Pre-flight cache uses a conid-only key — safe only because the cache is per-instance (latent foot-gun) — `Low`

**Location:** `src/IbkrConduit/Client/MarketDataOperations.cs:45,67,101,234`.

**What the code does:** `_preflightCache` is an instance `MemoryCache` (constructed in the ctor, not static) storing a boolean "pre-flight attempted" marker keyed by the bare integer `conid` with no account prefix. Registered per provider via the `AddSingleton<IMarketDataOperations>` factory.

**Impact on multi-instance:** No current defect — each credential's `MarketDataOperations` owns a private cache, so conid keys cannot collide across accounts. The safety is an implicit consequence of the per-instance registration shape, not an explicit guard: a future refactor that made this cache static/shared would silently mix pre-flight decisions across accounts.

**Recommendation:** Add a code comment at the cache field/key sites stating that conid-only keys are valid only because the cache is per-credential, so a maintainer does not promote it to a shared/static cache without re-scoping the keys.

**Confidence:** High.

### Consumer-owned `IbkrOAuthCredentials` (RSA keys) can be disposed while the session still needs them — `Low`

**Location:** `src/IbkrConduit/Auth/IbkrOAuthCredentials.cs:18-37`; `src/IbkrConduit/Http/SessionServiceRegistration.cs:48-51`; `src/IbkrConduit/Auth/LiveSessionTokenClient.cs:46-54`.

**What the code does:** `IbkrOAuthCredentials` owns and disposes two RSA keys. The object is captured by closure into the per-instance `SessionTokenProvider` and used on every LST acquisition, but it is never registered as a DI service, so the container does not own or dispose it — the consumer does (the E2E pattern is `using var creds = ...`).

**Impact on multi-instance:** Per-instance robustness only — not a cross-account isolation defect (each instance has its own credentials object). The risk is a consumer disposing one account's credentials too early relative to that same account's session lifetime, yielding `ObjectDisposedException` during proactive refresh / 401 reauth signing.

**Recommendation:** Document that credentials must outlive the provider (dispose the `ServiceProvider` before the credentials), or optionally allow the provider to take ownership.

**Confidence:** Medium.

## Confirmations (correct isolation)

These info-level findings are positive evidence that the multi-tenant design holds; I re-verified each against source.

- **No mutable static fields anywhere in `src/`.** A filtered grep for non-readonly/non-const static fields returned nothing. All credential-dependent mutable state (sessions, rate limiters, WS subscriptions, preflight cache, lifecycle subscribers, health state) lives on per-provider instances. (`src/` full sweep.)
- **Session & credential layer is fully instance-scoped.** `SessionManager`'s re-auth `_semaphore` and `_reauthEpoch`, `SessionTokenProvider`'s LST cache + `_semaphore`, the per-instance `TickleTimer` (own CTS + background task), and `OAuthSigningHandler`'s captured consumer key/access token are all instance state. A 401 storm or reauth on account A acquires only A's semaphore and signs only with A's credentials — wrong-account signing is structurally impossible. (`SessionManager.cs:46,56,61-63`; `SessionTokenProvider.cs:15-19`; `OAuthSigningHandler.cs:46-47,73`.)
- **Global and per-endpoint rate limiters are per-provider, not static.** `RateLimitingAndResilienceRegistration.Register` constructs fresh `TokenBucketRateLimiter` objects as locals and registers them into the per-call `IServiceCollection`; Flex burst/sustained limiters are likewise per-registration. Each credential gets its own 10 req/s global budget and its own per-endpoint buckets — accounts cannot throttle each other. There is no Polly pipeline holding cross-account retry/circuit state. (`RateLimitingAndResilienceRegistration.cs:16-23`; `StreamingAndFlexRegistration.cs:50-68`.)
- **WebSocket streaming is fully per-instance.** `IbkrWebSocketClient` holds the socket, heartbeat/message-pump/dispose CTS, the `_subscribers` channel registry, and the `_activeSubscriptions` replay list as instance fields, subscribes only to its own provider's `SessionLifecycleNotifier`, and creates a fresh adapter per connection. Two accounts hold two independent live sockets; account A's reauth/tickle reconnects only A's socket. (`IbkrWebSocketClient.cs:47-57,101-102`; `SessionLifecycleNotifier.cs:11-13`.)
- **Health state is per-provider instance state.** `SessionHealthState`, `LastSuccessfulCallTracker`, `HealthStatusOptions`, and `HealthStatusCollector` are `AddSingleton` on the per-call collection and aggregate only their own provider's injected dependencies — instance B cannot overwrite instance A's health. The `IbkrClient` facade holds only injected per-provider deps. (`ServiceCollectionExtensions.cs:68-83`.)
- **Tenant-keyed plain HttpClients.** The LST and Flex `HttpClient`s are named `IbkrConduit-LST-{TenantId}` / `IbkrConduit-Flex-{TenantId}`, so even in a shared container these specific clients do not collide (distinct consumer keys). (`SessionServiceRegistration.cs:31`; `StreamingAndFlexRegistration.cs:48`.)

## Reviewed and cleared (static-by-design, not issues)

These items are process-global by design and were confirmed to carry no per-credential mutable state — they are NOT findings:

- **`IbkrConduitDiagnostics.ActivitySource` / `Meter`** (`Diagnostics/IbkrConduitDiagnostics.cs:21-24`) and every `static readonly` Counter/Histogram/UpDownCounter instrument built from that `Meter` (e.g. `SessionManager.cs:26-35`, `IbkrWebSocketClient.cs:27-36`, the rate-limiting handlers). Write-once instrument handles; multiple instances correctly publish to the same named `Meter`/`ActivitySource` — the expected OTEL pattern. (The *values* they emit lacking a tenant tag is the separate Medium telemetry finding.)
- **`DtoFieldMap._cache`** (`Http/DtoFieldMap.cs:14-20`) — a `static readonly ConcurrentDictionary<Type, DtoFieldInfo>`. Genuinely process-global, but keyed solely by CLR `Type` and storing immutable, type-invariant JSON-schema metadata derived from attributes. Identical for every credential; worst case under concurrency is a redundant idempotent `ExtractCore`. A deliberate, safe cross-instance memoization. (Optional: add a comment noting it is intentionally process-wide and credential-agnostic.)
- **Immutable lookup tables / pure statics:** `FlexErrorCodes._codes`, `SuppressibleMessages.AutomatedTrading`, `MarketDataOperations._nonDataKeys`, `FlexOperations._pollDelaysMs`, `AuditLogHandler._flexTokenPattern`, `ResultFactory._jsonOptions`, and the static rate-limiter factory methods / `Streaming/Mappers` / crypto / parser helpers. All `static readonly` immutable data or pure functions — no per-credential state.

## Recommendations

Prioritized, actionable next steps:

1. **(Library, Medium)** Wire `LogFields.TenantId` through as a dimension on metrics, spans, and a per-instance log scope so multi-instance telemetry is attributable per account. This is the single highest-value change for the targeted topology.
2. **(Library, Medium)** Make multi-credential hosting safe by construction: either (a) guard against a second `AddIbkrClient` on the same `IServiceCollection` and throw a clear error, or (b) add a keyed/factory API (`AddIbkrClient(serviceKey, ...)` / `IIbkrClientFactory`) and tenant-name the consumer Refit clients to match the LST/Flex clients.
3. **(Library, Documentation)** Prominently document the supported contract in `AddIbkrClient`'s XML doc and README: **one `IServiceProvider` per credential**; do not register two credentials in one container with the current API.
4. **(Library, Low)** Capture and dispose the per-instance `ObservableGauge`s and tag them with the tenant id; register queue-depth once (e.g. via `HealthStatusCollector`) rather than per handler.
5. **(Library, Low)** Add invariant comments at the preflight cache key sites (conid-only key is safe only while the cache is per-instance) and document the credentials-lifetime contract (credentials must outlive the provider).
6. **(Consumer)** Until a keyed/factory API exists, host each credential in its own dedicated `IServiceProvider`/`ServiceCollection`, and dispose the provider before disposing that account's `IbkrOAuthCredentials`. Expect telemetry to lack per-account attribution until recommendation 1 ships.

## Methodology

Six independent lens-reviewers each returned structured findings, then the adjudicator **adversarially re-verified every load-bearing claim against `src/`** (ignoring `obj/` build artifacts) rather than trusting the finders. The lenses were:

1. **Static & process-global mutable state** — exhaustive sweep for mutable statics, `[ThreadStatic]`, `AsyncLocal`, static caches.
2. **DI registration, service lifetimes & N-instance hosting model** — `AddIbkrClient`, singleton lifetimes, Refit client naming, keyed-DI absence.
3. **Session & credential isolation** — re-auth/token semaphores, credential binding, tickle timers.
4. **Rate limiting & resilience isolation** — global/per-endpoint/Flex limiters, retry/refresh paths.
5. **WebSocket streaming isolation** — socket/timer/subscription registry scoping, lifecycle fan-out.
6. **Caching, cross-account data leakage & observability attribution** — preflight cache, `DtoFieldMap`, health state, telemetry dimensions.

Verification performed for this report: confirmed zero mutable static fields via filtered grep; read `RateLimitingAndResilienceRegistration`, `ServiceCollectionExtensions`, `ConsumerPipelineRegistration`, and `DtoFieldMap` to confirm per-call limiter construction, plain unguarded `AddSingleton`, type-name-keyed `AddRefitClient`, closure-captured credentials in `OAuthSigningHandler`, and the absence of any keyed DI; and grepped all `TenantId` usages to confirm it is wired only to HttpClient names, never to telemetry. Duplicate findings (the telemetry gap and the double-registration foot-gun were each raised by multiple lenses) were merged into single entries.
