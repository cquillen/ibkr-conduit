# RTOS venue-consumer review — IbkrConduit as the money boundary

**Date:** 2026-07-04 · **Reviewed at:** `main` @ `c7a07fd` (v0.8.0)

**Question under review:** what in IbkrConduit could cause the RTOS `IbkrVenue` (sibling repo `realtest-order-steward`, ADR-0028 + Stream IBV, merged 2026-07-04) to **lose money, duplicate orders, lose fills, or corrupt session state**? RTOS consumes this library at the `IIbkrClient`/`IIbkrClientManager` facade and assumes: the order-outcome trichotomy (definitively-transmitted / definitively-refused / ambiguous→InDoubt) is true; `str` executions are complete modulo `execution_id` dedup; `sor` frames are sparse deltas where *absent ≠ zero*; session/health signals are truthful liveness evidence; `IsPaper` gates a real-money interlock; and money numerics pass through uncorrupted.

**Method:** multi-agent adversarial review (46 agents). Five sweep lenses — ambiguity trichotomy, fill delivery, session lifecycle, manager/multi-client, wire fidelity — ran in bounded waves; every finding then went to an independent skeptic agent instructed to refute it against the actual code; a completeness critic named coverage gaps, which were probed and verified the same way. Read-only: no code changes, no live IBKR calls, no credential access. Severity is judged from the RTOS consumer's seat: **critical** = money loss / duplicate order / lost fill / corrupted money field; **high** = session/liveness integrity; **medium** = observability or robustness gap that hides one of the above; **low** = nit or unreachable through the public facade.

**Verdict meanings:** CONFIRMED = the skeptic independently traced the failure path end-to-end. PLAUSIBLE = the skeptic could not refute it, but full confirmation depends on unpinned live IBKR behavior. UNVERIFIED = swept up but not skeptic-checked (verification cap); treat as unconfirmed. REFUTED = the skeptic produced concrete counter-evidence; listed under "refuted claims".

**Result:** 33 verified findings (2 critical, 10 high, 19 medium, 2 low), 4 unverified overflow findings, 2 claims refuted, 53 areas deep-read and found clean.

## Verified findings

### FIL-1 — critical — IbkrWebSocketClient (per-subscriber str channel)

- **Where:** `src/IbkrConduit/Streaming/IbkrWebSocketClient.cs:221` · lens: fill delivery
- **Claim:** The per-subscriber bounded channel for every streaming topic (including str trade executions) uses BoundedChannelFullMode.DropOldest with capacity IbkrClientOptions.StreamingBufferSize (default 256), and an overflow drop is completely unobservable: Channel.CreateBounded is called WITHOUT the itemDropped callback overload, TryWrite under DropOldest always returns true so even the writer cannot detect the eviction, and there is no log line, no metric, and no consumer callback anywhere for a channel-overflow drop (the only 'dropped frame' logging in the codebase — StreamingObservableLog.LogDroppedFrame — covers mapper/OnNext failures, not overflow; grep confirms no other drop instrumentation exists).
- **RTOS consequence:** During a fill burst (e.g. the str replay-on-resubscribe snapshot RTOS explicitly depends on in its spec §10) or any stall in RTOS's inbound-adapter observer, execution frames are silently evicted before delivery. RTOS never books money that moved, and gets zero signal (no log, no metric, no OnError) that it should reconcile via GetTradesAsync — a silent lost fill on the money path.
- **Evidence:** src/IbkrConduit/Streaming/IbkrWebSocketClient.cs:218-223 (SubscribeTopicAsync channel: FullMode=DropOldest, no itemDropped callback) and 252-257 (RegisterUnsolicitedTopic, same); ProcessMessage writes with bare writer.TryWrite(root) at line 545 ignoring nothing because DropOldest TryWrite cannot fail; default capacity src/IbkrConduit/Session/IbkrClientOptions.cs:87 (= 256); wiring confirmed via src/IbkrConduit/Http/StreamingAndFlexRegistration.cs:31-47 (clientOptions.StreamingBufferSize -> IbkrWebSocketClient; StreamingOperations -> same client), and StreamingOperations.TradeExecutionsAsync (src/IbkrConduit/Client/StreamingOperations.cs:86-105) consumes that reader. No 'messages.dropped' counter exists in the Meter set (only received/sent/unsubscribe/reconnect/heartbeat, lines 27-40).
- **Skeptic verdict:** **CONFIRMED** — Every cited element checks out. IbkrWebSocketClient.cs:218-223 and 252-257 create the per-subscriber channel with BoundedChannelFullMode.DropOldest using the Channel.CreateBounded overload WITHOUT the itemDropped callback; ProcessMessage at line 545 ignores TryWrite's return (which is always true under DropOldest anyway), so eviction is invisible at both ends. The client's Meter set (lines 27-40, 114) has no dropped counter, and a repo-wide grep confirms the only 'dropped frame' instrumentation is StreamingObservableLog.LogDroppedFrame, which fires solely from the mapper/OnNext catch in FanOutChannelObservable.PumpAsync (FanOutChannelObservable.cs:61-64) — never on overflow. The path is fully wired into the RTOS facade: StreamingAndFlexRegistration.cs:31-47 passes clientOptions.StreamingBufferSize (default 256, IbkrClientOptions.cs:87, whose doc explicitly says the DropOldest policy is fixed and not configurable) into the singleton IbkrWebSocketClient consumed by StreamingOperations.TradeExecutionsAsync (StreamingOperations.cs:86-105, str topic). The trigger is concrete: PumpAsync invokes observer.OnNext synchronously inside the channel read loop, so a stalled RTOS observer or a >256-frame str replay burst on resubscribe fills the buffer and silently evicts the oldest execution frames with no log, metric, or OnError. The only test touching StreamingBufferSize (SessionModelsTests.cs:115) merely pins the default value of 256 — no overflow-observability test exists.
- **Failure scenario (refined):** During a str fill burst or replay-on-resubscribe snapshot exceeding 256 frames (or any stall in RTOS's synchronous OnNext observer), execution frames are silently evicted from the bounded channel before delivery: RTOS never books money that moved, and receives no log, metric, or OnError signal that it must reconcile via GetTradesAsync — a silent unbooked fill on the money path that also breaks the execution_id dedup/completeness assumption.
- **Suggested fix direction (conduit-side):** Use the Channel.CreateBounded<T>(BoundedChannelOptions, Action<T> itemDropped) overload to emit a Warning log plus a new counter (e.g. ibkr.conduit.websocket.messages.dropped tagged with tenant + topic) on every eviction; additionally consider making FullMode configurable per topic (Wait for money topics like str/sor) or exposing a drop notification the subscription surface can observe.
- **Suggested regression test:** SubscribeTopicAsync_BufferOverflow_EmitsDropSignal — with a stalled reader, write StreamingBufferSize+1 str frames via a mock WebSocket server and assert the drop counter increments (and/or the warning log fires) exactly once with topic=str; pins that an overflow eviction is observable.

### WIR-1 — critical — OrderUpdate (sor streaming DTO)

- **Where:** `src/IbkrConduit/Streaming/StreamingModels.cs:74` · lens: wire fidelity
- **Claim:** The OrderUpdate DTO erases field-presence information on sparse sor frames: Size, FilledQuantity and RemainingQuantity are non-nullable decimal (absent -> 0), Conid is non-nullable int (absent -> 0), and Status/Side/Symbol/OrderType default to string.Empty (absent -> ""). Only Price and OrderRef are nullable. A consumer performing a sparse-delta merge cannot distinguish 'field omitted from this frame' from 'field really is 0 / empty', so merged order state gets silently overwritten with zeros and empty strings.
- **RTOS consequence:** RTOS's IBV-06 merge cache is specified as 'only non-null frame fields overwrite; null fields never erase' (RTOS spec 2026-07-04, line 160/164). With this DTO, a sparse frame that omits filledQuantity/remainingQuantity/status presents FilledQuantity=0, RemainingQuantity=0, Status="" as non-null values — the merge regresses a partially-filled order to unfilled or blanks its status, corrupting the classification that drives cancel/replace and duplicate-order decisions.
- **Evidence:** src/IbkrConduit/Streaming/StreamingModels.cs:57-78 (Size/FilledQuantity/RemainingQuantity declared `decimal`, Status/Side `= string.Empty`); the repo's own live-captured sparse frame proves sparseness is real: tests/IbkrConduit.Tests.Unit/Streaming/OrderUpdateMapperTests.cs:13-14 — `{"acct":"DUO873728","conidex":"756733","conid":756733,"orderId":656804954,"isEventTrading":"0"}` carries no quantity/status fields at all; deserialized through StreamingSerialization.Options (StreamingSerialization.cs:17) it yields FilledQuantity=0m, Status="". Pipeline: IIbkrClient.Streaming.OrderUpdatesAsync -> OrderUpdateMapper.MapMany (Mappers/OrderUpdateMapper.cs:21) -> this DTO, no other guard exists.
- **Skeptic verdict:** **CONFIRMED** — Traced end-to-end and every factual element holds. (1) DTO: src/IbkrConduit/Streaming/StreamingModels.cs — Size (line 58), FilledQuantity (line 74), RemainingQuantity (line 78) are non-nullable decimal; Conid non-nullable int (line 46); Symbol/Side/OrderType/Status default to string.Empty (lines 50/54/62/70); only Price (66) and OrderRef (86) are nullable. (2) Sparse frames are real: live-captured fixture at tests/IbkrConduit.Tests.Unit/Streaming/OrderUpdateMapperTests.cs:13-14 carries no quantity/status fields; the repo's own example independently documents it at examples/IbkrConduit.Examples.OrderMonitor/LiveOrderTable.cs:62-66 ("every other field arrives at its default (empty string / 0 / null)") and has to work around it with a non-zero/non-empty heuristic merge. (3) Pipeline: IIbkrClient.Streaming.OrderUpdatesAsync (StreamingOperations.cs:73-82) -> OrderUpdateMapper.MapMany (OrderUpdateMapper.cs:21) -> Deserialize<OrderUpdate>(StreamingSerialization.Options) with no guard; StreamingSerialization.cs:22 additionally maps a present-but-empty "" to 0m via EmptyTolerantDecimalConverter. (4) No recovery path: [JsonExtensionData] AdditionalData (StreamingModels.cs:90) only holds unmapped keys, so an omitted filledQuantity leaves no trace — presence is irrecoverable. (5) The workaround the example uses is itself unsound for RTOS: it cannot distinguish a genuine RemainingQuantity=0 (fully filled) or FilledQuantity=0 from absence, so a correct sparse-delta merge is impossible over this DTO. No test pins nullable semantics; nothing refutes the claim.
- **Failure scenario (refined):** RTOS's IBV-06 merge cache applies its 'non-null frame fields overwrite' rule to an OrderUpdate built from a sparse sor delta: omitted filledQuantity/remainingQuantity/status arrive as non-null 0m/0m/"" and overwrite the cached state, silently regressing a partially-filled live order to unfilled (or blanking its status). RTOS then makes cancel/replace and duplicate-order decisions against corrupted fill state — e.g. re-submitting or up-sizing a replace for quantity that has already executed, producing a duplicate/oversized live order in a real-money account. Even a presence heuristic cannot fix it, because a genuine RemainingQuantity=0 (fully filled) is indistinguishable from an omitted field.
- **Suggested fix direction (conduit-side):** Make every sor field on OrderUpdate nullable (decimal?, string?) so an absent field maps to null and presence semantics survive; document that null means 'not present in this frame'. Optionally add a presence set or keep raw JsonElement alongside. This mirrors what was already done for Price.
- **Suggested regression test:** OrderUpdateMapper_SparseFrame_OmittedFieldsAreNull — deserialize the existing live-captured sparse frame (orderId/conid only) and assert FilledQuantity, RemainingQuantity, Size, Status, Side are all null (not 0m / ""), pinning that sparse frames never synthesize zero quantities or empty statuses.

### FIL-2 — high — TradeExecutionMapper + FanOutChannelObservable

- **Where:** `src/IbkrConduit/Streaming/Mappers/TradeExecutionMapper.cs:21` · lens: fill delivery
- **Claim:** TradeExecutionMapper.MapMany deserializes the frame's args array lazily (yield inside foreach), and FanOutChannelObservable wraps the whole enumeration+OnNext loop in a single per-frame try/catch — so one malformed element in a str frame's args array throws mid-enumeration and silently discards ALL subsequent executions in that frame, logged only as one 'Dropping a malformed TradeExecution frame' warning.
- **RTOS consequence:** The str subscribe/resubscribe snapshot is a single frame whose args array carries up to a whole day's executions (docs/ibkr-websocket-api-reference.md, 'Request Trades Data': args is an array of execution objects, days default 1). One execution with an unexpected field shape (a new non-numeric token, a shape the EmptyTolerant converters don't cover) drops the tail of the day's fills — RTOS's replay-absorbing LRU and execId dedup never see them, and its poison/IsParseable=false path cannot fire because the conduit discarded the elements before delivery. Unbooked fills with only a conduit-side warning log as evidence.
- **Evidence:** src/IbkrConduit/Streaming/Mappers/TradeExecutionMapper.cs:19-26 (lazy per-element element.Deserialize<TradeExecution> inside an iterator — an exception on element k propagates after elements 1..k-1 were yielded); src/IbkrConduit/Streaming/FanOutChannelObservable.cs:54-64 (the catch wraps 'foreach (var item in _mapper(frame)) { observer.OnNext(item); }' — the whole remaining frame is skipped on first throw); wired to str in src/IbkrConduit/Client/StreamingOperations.cs:104.
- **Skeptic verdict:** **CONFIRMED** — Traced end-to-end. TradeExecutionMapper.MapMany (src/IbkrConduit/Streaming/Mappers/TradeExecutionMapper.cs:19-26) is a lazy iterator with per-element element.Deserialize<TradeExecution> and no per-element try/catch; an exception on element k propagates through MoveNext after elements 1..k-1 were yielded. FanOutChannelObservable.PumpAsync (src/IbkrConduit/Streaming/FanOutChannelObservable.cs:54-64) wraps the entire 'foreach (var item in _mapper(frame)) observer.OnNext(item)' in one catch that logs LogDroppedFrame and skips to the next frame — elements k+1..n of that frame are never enumerated. The code comment at lines 49-53 even names 'one bad element within its args array' but the guard is frame-granular, not element-granular. Throw paths are real: StreamingSerialization.Options converters throw JsonException on non-Number/String/Null tokens (EmptyTolerantNumberConverters.cs:77,97) and int.Parse on non-numeric non-empty strings (line 237); plain string properties like Symbol/ExecutionId (StreamingModels.cs:220,224) throw on a numeric/bool/object token per STJ defaults. Wired into the RTOS path at src/IbkrConduit/Client/StreamingOperations.cs:104 (TradeExecutionsAsync, str topic). No test refutes it: FanOutChannelObservableTests.cs:87-135 pins only whole-frame isolation; TradeExecutionMapperTests has no mixed valid/malformed-element case. docs/ibkr-websocket-api-reference.md:318-330 confirms the str snapshot is one frame whose args array carries the day's executions (days default 1), and the replay-on-reconnect noted in StreamingModels.cs:210-213 means the same malformed element re-drops the same tail on every resubscribe — the loss is persistent. Concrete trigger: a str frame args array of [validExec, {"conid":{"x":1}}, validExec2] delivers only validExec; validExec2 is silently discarded with a single warning log.
- **Failure scenario (refined):** Unbooked fills: one execution object with an unexpected field shape early in a str snapshot frame silently discards every later execution in that frame before delivery — RTOS's execution_id dedup and poison/IsParseable path never see them, reconnect replay re-hits the same element and re-drops the same tail, and positions/cash in RTOS's write-ahead money protocol diverge from the venue with only a conduit-side 'dropped frame' warning as evidence.
- **Suggested fix direction (conduit-side):** Isolate failures per args element inside MapMany: deserialize each element in its own try/catch, log-and-skip only the bad element, and yield the rest (materialize the per-element result before yielding). Keep the observable-level catch as the last-resort frame guard.
- **Suggested regression test:** MapMany_OneMalformedElement_YieldsRemainingExecutions — a str frame with args [validExec, {"conid":"garbage-object"}, validExec2] must emit both valid executions through FanOutChannelObservable; pins per-element (not per-frame) failure isolation.

### GAP1-1 — high — OrderOperations.GetLiveOrdersAsync

- **Where:** `src/IbkrConduit/Client/OrderOperations.cs:213` · lens: gap probe: GetLiveOrdersAsync force-priming
- **Claim:** GetLiveOrdersAsync maps the API result via `apiResult.Map(r => r.Orders ?? new List<LiveOrder>())`, discarding OrdersResponse.Snapshot — the priming indicator added in #220 precisely because IBKR's /iserver/account/orders returns an unprimed (snapshot:false, often empty) first response, and force=true deliberately clears the cache and returns an empty array. Because IIbkrOrderApi is internal (src/IbkrConduit/Orders/IIbkrOrderApi.cs:8), no public path surfaces the flag; the conduit also does not re-poll until snapshot:true. An unprimed/force-cleared empty response is therefore returned as Success(empty list), byte-for-byte identical to 'genuinely zero live orders'.

Through this facade that is unknowable: RTOS can only do a blind two-call dance and hope the second call is primed. If a fake-empty snapshot feeds InDoubt repair, a transmitted order is classified never-transmitted and resubmitted — a duplicate live order (direct money loss).
- **Evidence:** src/IbkrConduit/Client/OrderOperations.cs:211-213 (Map discards Snapshot); src/IbkrConduit/Orders/IIbkrOrderApiModels.cs:170-177 (Snapshot XML doc: 'the first call returns false and must be repeated to obtain the full set' — the conduit documents the quirk on a field consumers cannot reach); src/IbkrConduit/Orders/IIbkrOrderApi.cs:8 (internal interface); docs/ibkr-web-api-spec.md:4160 (force: 'Submission will appear as a blank array') and :4169/:4239 (snapshot response field); /repos/realtest-order-steward/docs/superpowers/specs/2026-07-04-ibv-ibkr-venue-integration-design.md lines 57, 146, 160, 191 (hydration gate and resync verdicts depend on 'primed' GetLiveOrdersAsync).

### AMB-1 — refuted — TokenRefreshHandler + ResponseBodyCaptureHandler (401-retry raw-body loss)

- **Where:** `src/IbkrConduit/Session/TokenRefreshHandler.cs:92`
- **Original claim:** Any response obtained via the 401 buffer-and-replay path loses the captured raw body, silently disabling hidden-error (200-with-error-body) detection for that call. ResponseBodyCaptureHandler stashes the body in the ORIGINAL request's Options (ResponseBodyCaptureHandler.cs:30), but the retry response's RequestMessage is the CLONE built by CloneRequest (TokenRefreshHandler.cs:121-147), which copies headers only — never Options. ResultFactory.GetCapturedBody (ResultFactory.cs:175-185) therefore returns null and rawBody degrades to "" on 2xx, so DetectHiddenError never runs. A retried GET /iserver/account/orders that returns 200 {"error":"..."} deserializes into OrdersResponse(Orders=null) (Refit web defaults skip unmapped members; StrictResponseValidation defaults off and only logs) and GetLiveOrdersAsync maps it to Success(empty list) (OrderOperations.cs:213). Same fail-open for CancelOrderAsync (fake Success with OrderId=0) and GetOrderStatusAsync (garbage Success); a retried order-POST reject degrades to an opaque IbkrApiError(200, "Response body could not be deserialized", RawBody=""), losing the reject reason. The clone is also disposed via `using` while still referenced as retryResponse.RequestMessage.
- **Why refuted:** Empirically refuted by end-to-end reproduction with the repo's exact components (real ResponseBodyCaptureHandler + TokenRefreshHandler wired in the ConsumerPipelineRegistration.cs:91-102 order, real SocketsHttpHandler, Refit 12.1.0 as pinned in Directory.Packages.props:7, IbkrRefitSettings.Create()). Against a local server returning 401 then 200 {"error":"no brokerage session"}, the Refit IApiResponse's RequestMessage reference-equals the ORIGINAL request (not the clone), its Options contain the captured retry body, and ResultFactory.FromResponse returns Failure(IbkrHiddenError "no brokerage session") — not Success(empty). The finding's raw-HTTP observation is locally accurate (a raw HttpClient call on the same pipeline does show the clone as HttpResponseMessage.RequestMessage with no captured Options), but the conduit never consumes responses at that level: every operations class (src/IbkrConduit/Client/*Operations.cs) consumes Refit IApiResponse, and Refit's request builder reassigns resp.RequestMessage back to the original request message it built before creating the ApiResponse wrapper (proved behaviorally: ApiResponse<T>.RequestMessage reads HttpResponseMessage.RequestMessage when constructed directly, yet through a full Refit call it is the original — so Refit must reassign in between). ResultFactory.GetCapturedBody (ResultFactory.cs:177) therefore reads the original request's Options, where ResponseBodyCaptureHandler.cs:30 stamped the retry response body, and DetectHiddenError runs normally on the 401-retry path. All downstream consequences (GetLiveOrdersAsync Success(empty) at OrderOperations.cs:213, fake cancel success, lost order-reject RawBody) hinged on this refuted premise. The clone-disposal sub-claim is harmless: the disposed clone is only transiently referenced by HttpResponseMessage.RequestMessage until Refit overwrites it, and HttpRequestMessage.Dispose only disposes already-sent request content; nothing in the conduit dereferences the clone. Caveat acknowledged: the repo has no test pinning hidden-error-on-retry (all *_401Recovery tests retry into clean success bodies), and the behavior rests on Refit's RequestMessage reassignment — a pinned-version regression test as the finding suggests would still be cheap insurance, but the defect as claimed does not exist in the shipped dependency graph.

- **Refresh-lock / tickle / WS reconnect deadlock surface** — Session API pipeline has no TokenRefreshHandler and its OAuthSigningHandler has no ISessionManager (SessionServiceRegistration.cs:69-93), so ssodh/init and tickle can never re-enter ReauthenticateAsync; WS ConnectAsync calls EnsureInitializedAsync before taking _connectLock (IbkrWebSocketClient.cs:158-183) and the notifier-driven reconnect inside ReauthenticateAsync uses only session-pipeline calls — no lock cycle found.
- **TickleTimer loop permanence** — The loop cannot die from exceptions: all failures (including exceptions thrown by the reauth callback, and HttpClient timeouts which are wrapped to IbkrTransientException before reaching the OCE filter) land in the generic catch and continue at the 5s failure cadence; only genuine cancellation exits (TickleTimer.cs:155-233). The dead-session-detection blind spot is reported separately as SES-2.
- **WS reconnect watchdog redundancy and subscription replay** — Close frame, receive WebSocketException, and heartbeat send failure all funnel into ReconnectAsync under _connectLock; a failed single-shot reconnect is retried by the tickle-succeeded watchdog each healthy tickle; solicited subscriptions are registry-kept and replayed on every reconnect with cancel-message refcounting (IbkrWebSocketClient.cs:398-600). Contingent on the tickle loop staying healthy — the coupling is captured in SES-2.
- **SessionLifecycleNotifier delivery semantics** — Snapshot-under-lock iteration with per-subscriber try/catch means one throwing subscriber cannot suppress delivery to others or kill the reauth (SessionLifecycleNotifier.cs:37-89); subscribe/dispose is race-safe. Note it carries only 'refreshed' and 'tickle succeeded' events — session-death is intentionally signaled via the sts stream and health, not this notifier.
- **IIbkrClientManager add/remove concurrency and credential ownership** — Sentinel reservation prevents duplicate tenants; every AddAsync failure path disposes exactly the right objects (normalized creds on duplicate key; TenantBuilder disposes provider+creds on eager-init failure; the TryUpdate-loss path disposes the fully built tenant) and only retracts its own sentinel (IbkrClientManager.cs:20-60, TenantBuilder.cs:34-50, ManagedTenant.cs:18-31); RemoveAsync-during-build deliberately aborts the in-flight Add without resurrecting the slot.

- **Culture invariance in parse/format paths** — OAuth signing (OAuthEncoding.cs:40, LiveSessionTokenClient.cs:51/90, OAuthCredentialsFactory.cs:37/66), strike formatting (ContractOperations.cs:74), conid formatting (MarketDataOperations.cs:157), and all Empty-Tolerant/FlexibleString converters use CultureInfo.InvariantCulture — no culture-sensitive number handling found on any money or signing path.

No silent-coercion or round-trip defect found.
