# ADR-0009 — Positions/Trades cold-read: heuristic auto-retry-once

**Status:** Accepted · **Date:** 2026-07-13 — timing assumption verified 2026-07-14 by live probe (see Context); revised 2026-07-14 (attended grooming, pre-merge — RPD-06 has not shipped) to add Decision point 4a, closing a gap the first unattended ship-backlog attempt found: this ADR never said what happens when the retry call itself fails; revised again 2026-07-14 (attended design pass, still pre-merge) to **re-scope the retry to Positions only** — Trades' empty-triggered retry is removed (Decision point 1a) — and to state the retry's composition with 401 recovery (Decision point 5), after the second ship-backlog attempt's gate caught the Trades retry breaking the concurrent-401 dedup test (see Context addendum).
**Relates to:** findings P3, NC2 (`docs/findings/2026-07-13-rtos-probe-dossier-doc-scouting.md`); design doc §10.6 (sibling decision), new §10.7; live probe `recordings/coldread-rpd06/` (2026-07-14). **Implemented by:** RPD-06 (`docs/backlog.md`, Stream RPD).

## Context

`GetLiveOrdersAsync`'s cold-read behavior (design doc §10.6) is addressed by a **wire-reported** signal — IBKR's own `snapshot: bool` field on the live-orders response, which the library surfaces via `LiveOrdersSnapshot.IsSnapshot`. RTOS's 2026-07-13 probe found the same family of behavior on two endpoints that carry **no such wire signal**:

- `GET /portfolio/{accountId}/positions/{pageId}` returned field-sparse rows (`name`/`ticker` missing) on the session's first read, enriched on a second read (findings doc P3).
- `GET /iserver/account/trades` returned an empty result on the first call of a session despite trades existing (findings doc NC2, explicitly scoped by RTOS as *not* a conduit issue — it primes around this on its own side today).

Doc scouting (findings doc, headline cross-cutting observation) found this same pattern independently documented for a third endpoint (Watchlist: *"The first request may only return the values C, conid, and name values. Subsequent requests will add additional contract information"* — DOC-03) but found **no server-reported freshness/completeness field for Positions or Trades** anywhere in DOC-01, DOC-03, or DOC-05. Unlike LiveOrders, there is no wire-level flag this design can surface to distinguish "definitively enriched" from "possibly cold" for these two endpoints.

**2026-07-14 live-probe verification** (`ibkr-live-probe`, 3 fresh-session repetitions against the paper account — `recordings/coldread-rpd06/`): both hypotheses observed 3/3. Every fresh session's first Positions read was missing `name`/`ticker` (21 keys vs. 46 on the enriched read); every fresh session's first Trades read was `[]` despite the account holding 2 same-day trades. An **immediate, no-artificial-delay** second call reprimed both endpoints in all 3 repetitions — confirming the timing assumption in Decision point 1 rather than leaving it assumed. Sampling was homogeneous (one account, one instrument set, ~2 minutes) — this proves the pattern reliably appears and reprimes under these conditions; it does not rule out the residual adverse-timing race noted in Consequences. The same probe run incidentally found that `Position.strike` changes JSON type between the sparse first read (a number) and the enriched second read (a string) for the same rows — a nuance for RPD-05 (`docs/backlog.md`), not this ADR, but evidence that the cold/enriched read distinction this ADR addresses reaches beyond field presence into field typing.

**2026-07-14 addendum — the gate finding that prompted the re-scope.** The second unattended ship-backlog attempt (draft PR #305) implemented the original both-endpoints decision; its 14-agent review returned CLEAN, but the gate's full offline suite failed `Concurrent401_TriggersSingleReauth` deterministically (6/6 with the diff, 4/4 reverted): the Trades retry, firing on the post-recovery replay's empty result, received a **second** 401 and independently re-entered the full re-auth path — 2 LST acquisitions where the test pins 1. Attended reproduction traced the retry's 401 to a **WireMock scenario-cycling artifact**, not plausible IBKR behavior: a WireMock.Net scenario whose terminal stub lacks `WillSetStateTo` finishes and resets, so the test's stub pair serves `401, 200, 401, 200, …` cyclically (verified in isolation, 5-request probe, 2026-07-14). The mock-shaped trigger nonetheless exposed two genuine gaps this ADR had never recorded: the Trades trigger's imprecision carries a *recurring* cost the original point 4 mispriced as one-off, and the retry's interaction with 401 recovery was undecided. Both are closed by the revisions below.

## Decision

1. `GetPositionsAsync` **transparently retries once** when a read "looks sparse": a non-empty positions list with a returned row missing `name`/`ticker` — the cold-read signature captured 3/3 by live probe; an empty list is *not* sparse (a zero-position account never triggers a retry). The retry is immediate (no artificial delay) — verified sufficient 3/3 by live probe (see Context), not merely assumed by analogy to LiveOrders. *(Revised 2026-07-14: originally this point also gave `GetTradesAsync` a retry on an empty first read; that half is removed — point 1a.)*

1a. **(Added 2026-07-14) `GetTradesAsync` gets no retry.** One call; the result is returned as IBKR sent it; the cold-read caveat is documented on the method (XML docs) and in §10.7, and the re-read decision belongs to the consumer — the same inform-don't-act posture as `GetLiveOrdersAsync` (§10.6), minus the `IsSnapshot` flag IBKR provides no equivalent of for trades. The governing principle, now explicit: **the library auto-retries only on a wire shape that positively indicates incompleteness (rows present with expected fields missing); it never retries on absence of data**, because absence is also a legitimate answer. Three forces: **(a) trigger imprecision** — `[]` is indistinguishable from a genuinely quiet trading day, so the heuristic misfires on every trade-free poll, not once; **(b) recurring cost** — `/iserver/account/trades` carries IBKR's own `1 req/5 secs` endpoint limiter (§8.1), so the retry queues behind the token the first call just consumed and stalls up to ~5s — a tax paid on *every* quiet-day poll for the life of the session, which reprices the "one wasted call" cost point 4 originally accepted; **(c)** the live consumer (RTOS) already primes around this endpoint on its own side (findings NC2 explicitly scoped it as not-a-conduit-issue).
2. The retry is internal and does **not** change the method's public return type — no `IsSnapshot`-style wrapper is added, in contrast to `GetLiveOrdersAsync`. The retry is capped at one attempt (never a loop), bounding worst-case latency and rate-limit budget cost. *(Scope since the 2026-07-14 re-scope: Positions only, here and in points 3–4a.)*
3. An `Activity` tag/event records whether a retry occurred, for observability, without surfacing it on the DTO (per `.claude/rules/code-style.md`'s per-method `Activity` span convention).
4. This is accepted as a heuristic, not a verified contract: with no server signal, "looks sparse" cannot be distinguished from "is legitimately sparse" (a thin account whose rows genuinely omit those fields). A false-positive retry costs one extra API call and a small latency addition; it does not corrupt data or change the result the consumer ultimately sees. *(The Trades variant of this false positive — a quiet trading day — is exactly what point 1a rejects: for Trades the false positive was the common case, not the edge case.)*
4a. **(Added 2026-07-14) On a retry HTTP failure (500/503/timeout/etc.), keep the original first-read result rather than surfacing the retry's failure.** The retry exists purely to *improve* a read that already succeeded; it must never make the caller's outcome worse than if the retry had never been attempted. A transient failure on the optional retry call is not itself surfaced as a `Result.Failure` — the first successful (sparse-but-valid) result wins. This closes a gap the original decision left unstated (point 1 above only addressed the retry's own timing sufficiency, not its failure mode) — found and correctly blocked by an unattended ship-backlog run's review panel before this story ever merged.
5. **(Added 2026-07-14) The Positions retry participates in standard 401 recovery, unmarked and unmodified.** It is an ordinary idempotent GET in the pipeline: if it 401s, `TokenRefreshHandler` re-authenticates and replays it like any other request, and a 401-replayed *first* read that still looks sparse gets the retry on top (the compositions are independent). This composes with — and does not weaken — the concurrent-401 dedup guarantee (issue #168, pinned by `Concurrent401_TriggersSingleReauth`): that guarantee collapses re-auths *concurrent in flight*; a retry that 401s after an earlier recovery completed is a genuinely new failure, and a second re-auth is then the correct response, not churn. This also matches the library's one shipped operations-layer retry precedent — the market-data pre-flight retry in `GetSnapshotAsync` participates in normal 401 recovery today.

## Alternatives considered

- **Client-tracked `IsSnapshot`-style wrapper** (mirror `LiveOrdersSnapshot`'s shape, computed from "is this the first call since session init" rather than a wire flag): keeps the public-surface pattern consistent with §10.6, but pushes the retry-or-trust decision onto every consumer, when the library is positioned to absorb exactly this class of quirk (`.claude/rules/architecture.md`: "The library handles IBKR API quirks... so consumers don't have to"). Rejected as the sole mechanism; may be revisited by a superseding ADR if the retry-once heuristic proves too unreliable in practice.
- **Document-only consumer obligation, no code change**: cheapest, but leaves the burden on every consumer despite the library's stated mission, and doesn't match how `GetLiveOrdersAsync` (§10.6) already treats the same class of problem as the library's responsibility. Rejected.
- **Automatic internal priming call after session init** (a throwaway warm-up read before the consumer's first real call): best potential UX, and the 2026-07-14 probe's confirmation that an immediate call reliably primes both endpoints means this alternative is now more plausible than when this ADR was first drafted — it could subsume the retry-once mechanism by moving the "wasted" call to session-init time instead of the first real read. Still rejected for now: it adds latency to every session init (even ones that never read Positions/Trades), where retry-once only costs latency on the calls that need it. May be revisited by a superseding ADR if session-init latency proves not to matter in practice.
- **(Point 4a) Unconditional retry-result adoption on failure too** (win or lose, matching this ADR's original point-1 phrasing taken literally): rejected 2026-07-14. Letting a transient failure on the *optional* retry call turn an already-successful first read into a hard `Result.Failure` is a reliability regression relative to not retrying at all — worse than the false-positive-sparse cost point 4 already accepts, since that cost is "one wasted call," not "a successful read becomes an error."
- **(Point 1a) Keep the Trades empty-read retry — this ADR's original scope**: rejected 2026-07-14 (operator decision, attended design pass). The three forces in point 1a; decisive was consistency with the orders posture (`GetLiveOrdersAsync` informs, never re-reads) combined with the endpoint-limiter stall being a *recurring per-poll* cost, not the one-off this ADR originally priced.
- **(Point 1a) A client-tracked `IsSnapshot`-style wrapper for Trades instead of the removed retry**: still rejected (see the first alternative above) — with no wire flag, a client-tracked "first call of this session" boolean asserts more than the library knows, and it's a 📦 public-surface change carrying a heuristic. The quirk is documented; the consumer applies their own policy (the live consumer, RTOS, already does).
- **(Point 5) Fail-closed 401 opt-out for the retry** (a per-request marker honored by `TokenRefreshHandler`, like the existing tickle exclusion, so a retry that 401s is simply a failed retry → point 4a keeps the first result): rejected 2026-07-14 — machinery sized to a threat the attended reproduction showed was manufactured by the test's WireMock scenario shape; in production a retry-401 means the session genuinely died between two back-to-back calls, where a re-auth is the *correct* response; and it would diverge from the shipped market-data pre-flight retry, which participates in normal recovery.
- **(Point 5) Re-auth epoch inheritance** (the retry carries its logical operation's re-auth epoch; `SessionManager` dedups against it → at most one re-auth per logical read): rejected 2026-07-14 — three layers of plumbing (`ISessionManager` surface, Refit `[Property]` options, handler) to suppress a rare-and-correct second re-auth, and in the already-recovered case it still pays a doomed replay before failing into point 4a anyway.

## Consequences

- Not a 📦 public-surface change: `GetPositionsAsync`/`GetTradesAsync` return types are unchanged. Positions' internal read behavior gains a bounded retry; Trades gains only documentation. `feat:` vs `fix:` is decided at grooming from the spec.
- **Trades consumers own the cold-read re-read** (2026-07-14 re-scope): a first-of-session `GetTradesAsync` may return `[]` despite trades existing, with no wire signal and no library retry — the XML docs and §10.7 state the quirk and the consumer obligation. RTOS is unaffected (it already primes). This is a deliberate, recorded exception to the "library absorbs IBKR quirks" mission: absorbing *this* quirk means guessing on every empty read and paying the endpoint limiter for each guess.
- For Positions: reduces, does not eliminate, the chance a consumer observes a cold/sparse read — a consumer racing session init with its own first read faster than the retry can complete could still observe sparseness. This decision does not claim to make cold reads structurally impossible, only less likely, in contrast to §10.6's `IsSnapshot` which makes the sparse case *observable* even when it isn't prevented.
- Cost (Positions): a thin account whose rows genuinely omit `name`/`ticker` would pay one wasted retry per read. Accepted as low-severity — latency and rate-limit budget only, bounded to one extra call, and no endpoint limiter is registered for the positions path (§8.1) so the stall is global-bucket only.
- Cost (Positions, point 5): in the rare production case where the session dies between the first read and the immediate retry, the retry's 401 triggers a second, non-concurrent re-auth — correct behavior, but worth knowing when reading LST-acquisition telemetry.
- **Test-hygiene finding (2026-07-14, attended reproduction):** a WireMock.Net scenario whose terminal stub lacks `WillSetStateTo` finishes and **resets**, so the stub set cycles — `Concurrent401_TriggersSingleReauth`'s 401→200 pairs actually serve `401, 200, 401, 200, …`, modeling a server that alternates unauthorized responses forever. That artifact is what handed the Trades retry its second 401. With the Trades retry removed the suite passes unchanged, but the trap remains for any future in-operation follow-up call; harden that test's scenarios with explicit terminal states when next touched (carried in the RPD-06 spec).
- Follow-on (named): the point-5 composition statement holds implicitly for the library's other self-originated calls — the market-data pre-flight retry (`GetSnapshotAsync`) and the §10.6 background force-clear follow-up. Both participate in normal 401 recovery today; that is now the recorded convention, and any future opt-out routes through a superseding ADR, not a call-site hack.
- Follow-on: RPD-06's spec locks the "looks sparse" predicate against the 2026-07-14 probe captures (Positions: `name`/`ticker` missing) rather than guessing — the immediate-retry timing question `.claude/rules/backlog-format.md`'s loop-ready-empirics requirement flagged is now verified (homogeneous 3/3), with the residual adverse-timing race noted above as the only remaining caveat.
