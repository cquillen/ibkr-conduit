# ADR-0008 — Bracket/OCA group submission: per-leg outcome classification

**Status:** Accepted · **Date:** 2026-07-13 *(revised 2026-07-14, pre-implementation, after live-probe verification — the Context's speculative "failure-mode-dependent ordering" claim is corrected below with wire evidence; the core per-leg-classification decision is unchanged and strengthened, not falsified)*
**Relates to:** findings P1, P2 (`docs/findings/2026-07-13-rtos-probe-dossier-doc-scouting.md`); design doc §9.9 (sibling decision), new §9.11; live probe `recordings/rpd02-invalidchild-{a,b,c}-*/` (2026-07-14). **Implemented by:** RPD-03, RPD-04 (`docs/backlog.md`, Stream RPD).

## Context

RTOS's 2026-07-13 live-paper probe submitted a bracket group with a deliberately invalid child order. The response the conduit's `PlaceOrdersAsync` classifier surfaced was a normal-looking `OrderSubmitted` with `order_id="-1"`, `order_status="Failed"` — a shape that passes typed deserialization cleanly (both fields are well-formed strings) but is semantically nonsensical as a successful order. In the same exchange, IBKR **partially executed the group**: the parent order went live while the child was rejected.

`PlaceOrdersAsync`'s classifier (`OrderOperations.ClassifyOrderResponses`) reads only `responses[0]` from IBKR's response array and treats it as "the group's outcome," matching the method's documented public contract today: *"IBKR returns a single result for the group (the parent's outcome)... Child order ids are NOT returned here — query `GetLiveOrdersAsync` and correlate."* That contract assumes the array's first entry always represents the parent.

No IBKR doc source documents this response shape, the ordering of entries within a multi-leg response array, or a sentinel convention for a rejected leg, in either direction (findings doc P1/P2 — DOC-01, DOC-03, DOC-05, DOC-08 were all scouted; none corroborates or contradicts it).

**2026-07-14 live-probe verification** (`ibkr-live-probe`, 3 distinct invalidity mechanisms against the paper account, cleanup verified — `recordings/rpd02-invalidchild-{a,b,c}-*/`) replaced the original speculation with wire evidence, and it turned out richer than one sentinel shape:

- **The response is heterogeneous across invalidity mechanisms, not one consistent sentinel.** A bogus child conid produced a **bare `{"error": "..."}` object — no array at all**, the whole group hard-rejected with nothing transmitted. A negative child price reproduced RTOS's `order_id="-1"`/`order_status="Failed"` sentinel, in a 2-element array — but this time the **parent did not go live either** (`order_status="Inactive"`, the whole bracket rejected together). A mismatched-instrument child produced **no sentinel at all** — a 2-element array where both legs got real order IDs after a confirmation-question chain, and the parent *did* go live (matching RTOS's original narrative, but via a different response shape than the sentinel case).
- **Where an array does appear, the child is structurally `responses[0]` and the parent is `responses[1]`**, in both observed array-shaped samples — not an incidental reordering specific to the failure mode, as originally speculated. The parent is identifiable by carrying `local_order_id` (the echoed cOID); the child in the confirmation-chain case instead carries a previously-undocumented `parent_order_id` field linking it back. Ordering held in both samples but is not a documented IBKR contract — classification must not rely on position even though it happened to correlate with role here (see Decision, point 1).
- **The parent does not always survive.** RTOS's narrative ("parent live, child dead") is one of at least two distinct outcomes the wire produces for an invalid child — the negative-price mechanism rejected the whole bracket together.
- A fourth invalidity mechanism from the original probe plan — a child's `parentId` not matching the parent's actual cOID — turned out to be **unreachable via the library**: `OrderOperations.ValidateOrderGroup` already throws client-side before any network call when linkage is malformed, so that case cannot occur on the wire through `PlaceOrdersAsync` today.

## Decision

1. `PlaceOrdersAsync`'s response classification changes from "index 0 is the group's single outcome" to a **per-leg outcome breakdown**: every leg present in IBKR's response array is classified independently — as a transmitted order (`OrderSubmitted`-shaped), a definite rejection (`IbkrOrderRejectedError`-shaped — covering the existing `{"error": "..."}` shape, the `order_id`-sentinel shape, and any row whose `order_status` is a terminal non-transmitting value such as `"Failed"` or `"Inactive"` regardless of what `order_id` it carries), or — for a leg present in the *request* with no corresponding entry in the *response* — an ambiguous outcome (`IbkrAmbiguousOrderError`, reusing ADR-0003/ADR-0006's existing "sent, outcome unknown, reconcile before resubmitting, never re-place" semantics). **Classification keys on each row's own field signature (`local_order_id` presence, `parent_order_id` presence, `order_id`/`order_status` values) — never on array position.** The probe's `responses[0]`-is-the-child pattern held in 2/2 array samples but is not a documented contract; a spec or implementation that hard-codes position instead of signature would be reintroducing the exact class of bug this ADR fixes, just with the index flipped.
2. When the response is **not** an array at all — a bare single-object hard rejection (observed for a bogus conid) — the existing whole-call `IbkrOrderRejectedError` classification (AMB-4) applies as-is: there is no per-leg data to break down, because IBKR rejected the submission before assigning any leg an identity.
3. `PlaceOrdersAsync`'s public return type changes to expose the per-leg breakdown for the array case, and the existing single-error classification for the no-array case. The exact shape (e.g. an `OneOf<IReadOnlyList<OrderLegOutcome>, OrderConfirmationRequired>`-style contract, with the no-array case surfacing as a `Result` failure rather than a populated leg list) is finalized in RPD-03's spec, not this ADR. A group confirmation-required response remains a single event for the whole group, unchanged — a question blocks transmission of every leg alike, so there is nothing to break down per-leg yet.
4. **This rule applies only to `PlaceOrdersAsync` (multi-leg groups).** `PlaceOrderAsync` (single-order submission) keeps its existing classification unchanged — a single order has no sibling leg that could plausibly have transmitted, so the "maybe it's ambiguous because a sibling might be live" concern that motivates per-leg classification for groups does not apply there.
5. The XML doc claim "Child order ids are NOT returned here — query `GetLiveOrdersAsync` and correlate" becomes false and must be corrected once RPD-03 ships. `GetLiveOrdersAsync` correlation remains the right tool for whatever this classification cannot resolve (the ambiguous, leg-missing-from-response case, and reconciling the true state of a hard-rejected group with no per-leg data), not for the general case.

## Alternatives considered

- **Collapse the whole group to `IbkrAmbiguousOrderError`** whenever any leg looks sentinel-shaped: reuses existing infrastructure with zero new types, and is strictly safer than the status quo (never claims success or failure when evidence is mixed). Rejected as the *primary* mechanism — it under-uses the evidence IBKR actually returns. When the response array shows a real order id for the parent and a sentinel for the child, we know precisely what happened to each leg; collapsing that to blanket "ambiguous" discards information the response already gave us and forces every partial-failure bracket through an extra `GetLiveOrdersAsync` round-trip the response itself made unnecessary. (Ambiguous classification is retained at per-leg granularity, for the one case where evidence is genuinely missing — a requested leg absent from the response.)
- **Collapse the whole group to `IbkrOrderRejectedError`**: the original bug's failure mode — risks telling the consumer "nothing happened" while a parent leg is actually live, inviting a dangerous duplicate resubmission. Rejected on safety grounds.
- **Status quo (`responses[0]` is the group outcome)**: blindly trusts response-array ordering to put the representative entry first, which both RTOS's observation and the 2026-07-14 probe falsify under partial-leg failure. Rejected — this is the defect being fixed.
- **Classify by array position** (now that the probe shows child-first held in both samples): rejected even though it would "work" on the evidence collected so far — position is not a documented IBKR contract, n=2 is too thin to promote an incidental correlation to a rule, and it reintroduces exactly the fragility this ADR exists to remove. Field-signature classification is strictly more robust and no more expensive to implement.

## Consequences

- 📦 **Breaking** (`feat!:`): `PlaceOrdersAsync`'s return type changes shape for every caller, including the happy path (all legs transmitted) — not just the failure path. RTOS and any other bracket/OCA consumer must migrate to iterate per-leg outcomes.
- Enables precise per-leg reconciliation directly from the submission response in the common case, without a follow-up `GetLiveOrdersAsync` call; that call remains necessary for the residual "leg missing from the response" case and for the no-array hard-rejection case (where nothing per-leg is knowable from the response at all).
- `PlaceOrderAsync` (single-leg) is unaffected — no migration needed for consumers that only ever submit single orders.
- Cost: more invasive to implement and to consume than a simple field promotion; `PlaceOrdersAsync`'s classification path now diverges from `PlaceOrderAsync`'s (they can no longer fully share `ClassifyOrderResponses`/`ClassifyResponse`); the classifier now has to branch on three response shapes (array with sentinel, array with real IDs, bare single-object reject), not one.
- Follow-on: RPD-04 (typed fields on order-submission response models) grows one field — the previously-undocumented `parent_order_id` (distinct from the `parentId` request field and from `LiveOrder`'s response-side `parentId`, RPD-02) — alongside `text`/`warning_message`/`messageOptions`, attaching to whichever per-leg outcome type this decision produces.
- **Verified, not merely assumed, as of 2026-07-14:** the per-leg classification approach is the right fix (confirmed by observing genuinely mixed per-leg outcomes on the wire); the "index 0" bug is root-caused precisely (child-first is structural in the samples observed, not an accident of one failure mode). **Still open for RPD-03's spec:** the full enumeration of terminal non-transmitting `order_status` values (`"Failed"`, `"Inactive"` observed; others may exist), and whether n=2 array-shape sampling is sufficient before this ships as `Risk: high` order-placement code, or whether grooming wants additional samples first.
